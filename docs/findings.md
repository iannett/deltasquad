# Findings

What is known about `Default.xbe` and the game data so far.

## Executable

| | |
|---|---|
| Original name | `XBoxLaunch.exe` (`C:\CT\BuildTemp\XboxShipping\`) |
| Build date | 2005-01-26 |
| Base address | `0x10000` |
| Xbox SDK | XDK 5849 for every library (Visual C++ 7.1) |
| Code (`.text`) | about 2.9 MB, 10,437 functions after analysis |
| Debug info | None. No symbol file, no RTTI for game classes |

### Sections

| Section | Contents |
|---|---|
| `.text` | Game, engine, C runtime and Xbox system code |
| `D3D`, `D3DX`, `XGRPH` | Direct3D 8 and graphics helpers |
| `DSOUND`, `XACTENG`, `WMADEC` | Audio |
| `XNET`, `XONLINE`, `XON_RD` | Networking and Xbox Live |
| `XMV` | Video playback (`.xmv` movies) |
| `XPP` | Controller and memory unit drivers |
| `DOLBY` | Dolby audio encoder data |
| `.rdata`, `.data` | Constants and globals, including the native function table |

Microsoft libraries outside `.text` are already separated by section. Inside `.text`, the C runtime and Xbox system code sit mostly in three ranges near the start and end of the section. `tools/progress.py` excludes them.

## Native function table

The engine keeps a table in `.data` of `{name, exec function, native index}` entries, one block per class. It connects each `native` function in the scripts to its C++ code.

- 737 entries found, 732 matched to a script class (`tools/find_natives.py`, output in `symbols/natives.csv`).
- A class with one native has a one-entry table. These are found by the null entry that ends every table.
- The 5 unmatched entries are network functions (`SendBinary`, `ReadBinary`, `BindPort`, `SendText`, `ReadText`) whose class is not in the shipped scripts.
- The first 717 are named in the Ghidra project as `Class::execName` (e.g. `AActor::execAddToSquadInterest`). The 20 one-entry tables found later are not named there yet.
- The packages declare 752 natives. Every one except `GameEngine.GetLocalizedKeyName` has an entry. That name is not in the executable at all.

## Gameplay scripts

- 21 packages, 1,302 classes, about 153,000 lines once decompiled (`tools/uscript-decompile`).
- Unreal package version 159, licensee 1. UELib detects the build as Republic Commando.
- 12 menu classes have errors in their `defaultproperties`. Function code decompiles cleanly.
- Most gameplay logic (AI orders, weapons, squad commands, menus) is UnrealScript. The C++ side is the engine plus the natives those scripts call.

## Engine differences found while decompiling

- **FName** stores a pointer to its `FNameEntry` instead of an index. `NAME_None` is a null pointer. Stock UE2 stores an index.
- **FName lookup modes**: besides find and add, there are two "defining" modes that fix a name's spelling (flag `0x80`). Adding the same name with a different case after that is a fatal error.
- **FNameEntry** layout: `Index`, `Flags`, `HashNext`, then the string, allocated only as long as the string needs.
- **TArray** keeps flags in the top 3 bits of its count and max fields (`(Num << 3) >> 3` everywhere).
- **Link-time code generation**: the game was built with LTCG, so many internal functions use custom register calling conventions. Ghidra's decompiler often drops their arguments. Reading the disassembly (`tools/ghidra.sh Disasm.java <address>`) recovers them.
- **384 hardcoded names**, regenerated by `tools/extract_names.py` into `src/Core/Inc/UnNames.h`.

## Classes and vtables

- Each native class is a static `UClass` built at startup by the UClass native constructor (`0x0009a85b`), called from small initializers near the end of `.text`.
- `tools/find_classes.py` reads all 494 registrations into `symbols/classes.csv`: name, package, parent, size, flags, constructors and vtable. 467 vtables were recovered. The other 27 classes share a placeholder constructor (mostly abstract classes).
- `UObject` is 40 bytes, its constructor is `0x00022c53` and its vtable is `0x003b4e30`.
- Class names in the executable are often the tail of a longer pooled string, so searching for a class name string finds few references.
- In the `FArchive` vtable, `operator<<(UObject*&)` is slot 0x24 and `operator<<(FName&)` is slot 0x28. The port declares them in the other order, which changes nothing at run time.
- The linker merged functions with identical code. The old font character serializer is the same function as `operator<<(FArchive&, FGuid&)` (`0x000b17ef`).

## Function coverage

Ghidra's first pass missed about 15% of the code (functions reached only through vtables and other pointers). `tools/ghidra/FindMissedFunctions.java` created 2,807 more functions, bringing 98% of `.text` into functions. Most of the rest is padding.

## Object system notes

- Objects created without a name get `NAME_InGameTempName` (920) and are never hashed, unless their class is a property, state or function class (`CLASS_UniqueNames`), which get `ClassName123`-style names.
- The `UClass` field at `0xe8` points at the class itself after construction. Defaults are read through it.
- `UStruct::Link` moves every non-property child to the front of `Children`, so `PropertyLink` plus `Next` walks only properties. `Vector` is forced to 12 bytes, `Plane` and `Quat` to 16.
- Replicated properties with byte-identical replication conditions share a `RepOwner` (`UProperty` offset `0x3c`).
- `UPackage::BindPackage` always succeeds on the Xbox (a dummy handle), since all native code is linked into the executable. The port keeps that behaviour.
- Startup order: `FName::StaticInit`, then `UObject::StaticInit`, which registers every native class through `ProcessRegistrants`. The first run of this on macOS registers the 25 Core classes plus the `Core` and `Transient` packages.
- `UObject::PostLoad` sets `RF_PerObjectLocalized` on every loaded object except those of class `ACTION_ShowPrompt`, then calls `LoadLocalized`. So in SWRC loaded objects read localized text by their own name, not their class name.
- `Localize` returns the key unchanged until `GIsStarted` (0x45a738) is set, which the game's main does first thing. A missing key is retried in the `int` files, then logged under `NAME_Localization` and returned as `<?lang?Package.Section.Key?>` unless optional.
- SWRC states keep a 128-bucket hash of their functions, states and structs (`UState+0x90`, chained through `UStruct+0x2c`). `UState::Link` builds it on a copy of the parent's hash; `FindFunction` uses it.
- `UClass::Link` stops the game ("VERIFY: Class %s size problem") when a native class's script size differs from its C++ size.
- `UFunction::Bind` looks up natives without an index by name in their own class's native table, and a miss is fatal. So every native class with script natives needs its table, even before the natives are decompiled. `Commandlet.Main` is in such a table but was missed by `find_natives.py`.
- `UCommandlet::Main` (vtable slot `+0x78`) is a thunk that calls the same slot again, so it never returns if called.
- `LoadPackage` assigns over its "package " context string instead of appending to it.

## Package loading notes

- Version 159 packages add a compact index after each export's package index (`FObjectExport::Unknown0C`). When it is set, `CreateExport` and `Preload` first handle every export from `Unknown0C - 1` up to the current one, so it marks where an export's dependencies start.
- The linker keeps a name only if its flags match the context (`RF_LoadForClient` `0x10000` when `GIsClient`, `RF_LoadForServer` `0x20000` when `GIsServer`). Other names load as `None`.
- From version 158, when a package's first import is another package, the linker opens that package's linker and registers itself as its `ChildLinker`. Core.u's first import is `Core` itself, which skips this.
- `ArSkipObjectRefs` (archive byte `0x17`) also makes name arrays read and discard their contents.
- Core.u: 408 names, 17 imports, 809 exports, one generation. All of its imports resolve inside Core, one of them to the native `Const` class.
- `CreateExport` never creates objects whose class is named `Camera` or `PlayerInput`.
- Package flag `0x20` makes `LoadAllObjects` preload every export with progress updates, and `VerifyImport` searches only the newest linker with this flag before falling back to the import's own package.
- Load flag `0x10` means "only check": `ULinkerLoad::Create` returns `(UObject*)-1` instead of creating, and `GetPackageLinker` skips import verification.
- `ULinkerLoad` offset `0xc4` is set to 1 by `Verify`, but `Preload` also stores the loader's file position there.
- `VerifyImport` accepts native classes with class flag `0x1000000` without looking for them in a package file.
- `GetPackageLinker` checks `CompatibleGuid` for every package except names containing `_Voice` or starting with `DM_` or `CTF_`.
- `Preload` runs a list of timed callbacks unless `GIsLevelLoading` (the value `IsLevelLoading` returns) is set. Nothing in Core adds one.
- `UField` has no `Serialize` of its own; it shares one thunk with `UPackage` that jumps to `UObject::Serialize`. `UStruct::Serialize` stores the `Next` link of every child, so fields never serialize their own `Next`.
- `UStruct::Serialize` ends by taking an MD5 of the script bytecode into 16 bytes at `UStruct` offset `0x68`. On the Xbox the bytecode holds live pointers, so the digest changes from run to run. Nothing in Core reads it.
- `UState` offset `0x88` is the state flags (serialized after `LabelTableOffset`). Offset `0x90` points to a 0x200 byte block that `Serialize` only counts for memory statistics.
- `UClass` offsets `0xbc`, `0xc4`, `0xcc` (defaults) and `0xd4` are four arrays; `~UClass` frees all four. `UClass::Serialize` reads the class dependencies, package imports and hide categories into locals and discards them.
- A class named `<Super>Defaults` (`UClass::IsDefaultsClass`) holds default properties for its parent. Loading it writes its tagged properties into the parent's defaults and renames its subobjects into the parent. Every other class tries `StaticLoadObject("Properties.<Name>Defaults")` quietly after loading its own defaults, unless archive byte `0x16` is set.
- `SerializeTaggedProperties` handles a property named `HSPass` with array index 0 by reading a second full property list into the same object. A byte value stored for a float property is converted. Properties with flag `0x200000` (`CPF_Static`) are only compared against the default when the last argument is set, and a mismatch is logged as "Static property ... legacy value".
- `SerializeBin` skips `LitDirectional` and `DisregardTerrainLighting` of `DecorationLayer` structs in packages older than version 115.
- After every function call in bytecode, `SerializeExpr` peeks at the next token. If it is `EX_DebugInfo` (`0x42`) with version 100, the debug info is read as part of the call.
- Bytecode differences from stock UE2: `EX_BoolVariable` (`0x2D`) has no operand, `EX_DelegateFunction` (`0x43`) is an object and a name with no parameter list, and `EX_DebugInfo` is three ints and a string.
- `StaticLoadObject` returns an existing object at once if it is loaded or waiting to load (`RF_NeedLoad` or `RF_WasLoaded`). Load flag `0x40` skips package files entirely and `0x2000` returns null for a missing object instead of throwing. Inside a nested load, the newest linker with archive byte `0x16` set gets the first try.
- Each class's destructor calls `ConditionalDestroy` while its own vtable is still in place. `StaticAllocateObject` relies on this when it replaces a native class in place with the copy from a package.

## Startup and config notes

- `appInit` (`0x37265`) order: CRC and bit length tables, log devices, names, `appPlatformPreInit`, file manager, version logs (build 139, engine version 2226, compiled Jan 25 2005), `GConfig` from a factory and `Init("System.ini", "User.ini")`, language, `UObject::StaticInit`, `GMem.Init(65536)`, `appPlatformInit` (creates `GSys`, marks the `Suppress` names, seeds the random numbers, then Xbox CPU detection). `-nolinear` turns off `bLinearLoad` and `bLinearSave`.
- `appInit` also allocates a 16-entry pool (`0x359e2`) that nothing but its own cleanup (`0x36831`) touches. The port leaves it out.
- `GConfig` exists before `UObject::StaticInit` because `USystem` loads its defaults from `[Core.System]` when it registers.
- `USystem`'s string and array members are never touched by its C++ constructor (the engine's `FStringNoInit` and `TArrayNoInit`), so the config values copied in by `StaticAllocateObject` survive. Destroying an array frees it and leaves it empty, which the engine relies on when `ExitProperties` and the C++ destructor both destroy it.
- The ini cache keeps a dirty flag per file, per section and per value. Values match case-insensitively, and the same nonzero number written differently (`1.0` and `1`) is not a change.
- `Flush` writes only files that changed, with unchanged values commented out as `;  Key=Value`. `User.ini` goes to the profile's directory (`0x45a808`, empty until a profile is chosen) and other files to `0x45a820`, which starts as `<INVALID>` and blocks saving until the launcher sets it. A new file needs 16 KB free on `U:`.
- Reading `User.ini` or `System.ini` also reads the copy in those directories over the disc's copy.
- Package search (`appFindPackageFile`): a name with an extension is tried as a path and relative to the base directory, then each `Paths` entry (skipping ones containing `Linear` unless `bLinearLoad`), localized `Name.<lang>_ext` before `Name.ext`, then the mod directory, then the cache when a guid is given. Names ending in `.dll` are never found.
- Log messages are dropped when their event name has flag `0x1000` (set from `[Core.System] Suppress=`).

## Port decisions

- Xbox drive paths `T:\`, `U:\` and `Z:\` (title data, saves, scratch such as `Z:\Out\`) map to `~/Library/Application Support/deltasquad/<letter>/` on macOS, never into the game files.
- `D:\` (the disc) maps to the parent of the base directory, so it is an absolute path and does not depend on the working directory.
- Pending: the game reads `Z:\Movies\Menu_BG.xmv` after copying it there from the disc. The port has to do that copy once the movie code is decompiled.

## Generated native classes

The native classes of every game package and the native layout tables are generated from the packages. Do not edit the output; rerun the generator.

```
dotnet tools/layout-dump/bin/Release/net10.0/layout-dump.dll game/System layouts.json
python3 tools/gen_layouts.py layouts.json                    # check every class against its xbox size
python3 tools/gen_layouts.py layouts.json generate Core Engine Gameplay CTGame CTMarkers IpDrv XGame XInterface XInterfaceLive
```

- Output per package: `src/<Package>/Inc/<Package>Classes.h`, `src/<Package>/Src/<Package>Classes.cpp` and `src/<Package>/Src/<Package>NativeStubs.cpp`. Core gets only `src/Core/Src/CoreStructLayouts.cpp`.
- Loading Engine.u pulls in the other packages: string properties with an object path preload that object, and Engine classes name CTGame classes this way. So every game package with native classes is a module. The Xbox platform drivers (D3DDrv, XboxDrv, XBoxAudio) are left out.
- Each class gets its native function table, in xbox table order, with `IMPLEMENT_NATIVE_TABLE` after the `IMPLEMENT_CLASS` lines. Script binds natives by name when a package loads, and a missing one is a fatal error.
- `<Package>NativeStubs.cpp` has a stub for every native that is not written yet. A native written by hand anywhere else in that package's `Src/` is left out of it on the next run.
- Native classes without script are generated as shells: the xbox parent, flags and within class, and no members. Their members are added in their cpptext file when their code is decompiled.
- Only script structs declared in native classes, or used by their members, are generated. The xbox headers had no others, and two packages declare different structs with the same name in script-only classes.
- Hand-written methods and members for a class go in `src/<Package>/Inc/CppText/<C++ class name>.h`. The generator includes that file in the class body when it exists.
- `CPP_MEMBER_TYPES` in the generator gives the real C++ type of a script placeholder (`Texture.Mips`, `Sound.Data`). `CPP_TYPE_HEADERS` lists the hand-written headers those types need.
- On the xbox, `UClass::Link` checks that a native class's script layout is exactly its C++ size. C++-only members appear in script as `native` placeholders, so script fixes the whole layout. 377 of the 494 native classes match their xbox size this way. The 10 XInterface menu classes do not, because their UI structs are a different size in C++. The other 107 have no script and are written by hand.
- Members are declared in script order. A byte-aligned member that starts a class or follows a bool group is pinned to 4 bytes, and each bool group starts a new word. This matches the xbox compiler, which never packs into a parent's tail padding or a bitfield word.
- Script structs that have a C++ type use its size, so arrays of them step the same way in script and C++.
- On 32-bit targets the generated source asserts that every class without strings or arrays is exactly its xbox size (88 classes). Strings and arrays are 12 bytes in the port and 8 on the xbox.

## 64-bit deviations

- Property placement (`Link`) and struct alignment use each type's C++ alignment via `UProperty::GetLinkAlign`. On 32-bit targets this gives exactly the Xbox offsets.
- The pre-registration auto-register link shares storage with `_LinkerIndex` through a union instead of being stored in an `INT`.
- Element sizes come from `sizeof` the real C++ types, so pointer-holding properties grow on 64-bit.
- `UObject::IsValid` is a member on the Xbox and is called on null pointers. Here it is static, since a null `this` is undefined behaviour.
- Script bytecode keeps object and name references in 4 bytes, so code offsets match the packages: an object is its `GObjObjects` index plus one (0 is null) and a name is its name index. See `ReadScriptObject` and `ReadScriptName`.
- Native classes keep their C++ layout. `FNativeLayout` (UnClass.h) lists, for each native class, the C++ offset of every script property it declares plus the class size and alignment. `UStruct::Link` uses it for those classes and stops with an error if a property has no entry. Script-only classes start after the native size. `Object.ObjectInternal` (six ints for the object header) is placed at 0 and `Subsystem.ExecVtbl` at the `FExec` base. Both are `CPF_Native`, so nothing copies or serializes them. On 32-bit targets the table gives the Xbox offsets. Core's tables are hand-written; Engine's should be generated.
- Bytecode handlers that share one body on the Xbox are split where 4 bytes is not enough on 64-bit: `IntConst`/`ObjectConst`/`NameConst`, `IntZero`/`False`/`NoObject`, and the `IntToBool`/`ObjectToBool`/`NameToBool` casts.
- `Context` and `ClassContext` zero the result with the size stored in the bytecode when the object is None. That size is the Xbox size, so a 64-bit pointer result only gets its low 4 bytes cleared. Callers so far pass zeroed buffers.
- `Let` writes through None into a scratch buffer. It is 8 bytes on the Xbox and 1024 here. Statement and switch buffers clear `sizeof(FString)` bytes, which is the 8 bytes the Xbox clears.
- The script debugger hooks (`0x45a764`) are left out. Nothing in the game sets that pointer.
- The `==` and `!=` natives for ints and objects share one body on the Xbox. They are split here so object pointers compare at full width.

## Platform deviations

- `Sqrt` and `appSqrt` use an exact square root. The Xbox inlines an SSE reciprocal square root estimate with one Newton step. That estimate differs between CPU makers, so it cannot be copied exactly.
- `appRand` scales the host's `rand()` into 0 to 32767, the Xbox range, so `Rand`, `FRand`, `VRand` and `RotRand` see the same ranges. The sequences still differ.
- The `<<` and `>>` vector-by-rotator natives inline `FCoords` math on the Xbox. Here they use the rotation matrix, which gives the same result up to float rounding.

## Bugs kept from the original

- `Invert` (Object.uc) builds a matrix whose fourth row is all zero, so `FMatrix::Inverse` always finds it singular and returns the identity. The three vectors always come back as the unit axes.
- `FQuat(const FMatrix&)` matches the usual conversion only when the trace is positive. In the other three cases the largest component gets 0.25 / root instead of 0.5 * root, and W uses sums instead of differences.
- `UClass::ResetConfig` reads the section from "System.ini" or "User.ini" and writes it back to the class's config name. Both resolve to the same cached file, so it writes the values back unchanged.
- `Disable` warns with "Enable: '%s' is not a probe function".
- `UObjectProperty::ImportText` skips one character after a plain object name, whatever it is, because it steps past the character it checks for a quote.
- `appExit` does not end the program. `UClass::Link` calls it on a size mismatch and keeps going.
- `UTexture::Serialize` reads and drops an old compressed mip array when the package is older than version 84 and bit 10 of the texture's bool word is set. No script bool is bit 10 (`bHasComp` is bit 8) and nothing sets it, so this never happens. The port leaves the branch out.
- `GUglyHackFlags` flag 8 changes how lazy arrays, materials and mips load, but nothing on the xbox sets it.

## Other port deviations

- `FName::StaticExit` logs memory use from sizes it adds up itself. The Xbox gets them from `FArchiveCountMem`, which asks the Xbox allocator.
- `UDelegateProperty::ImportText` stops its name buffers at `NAME_SIZE`. The Xbox does not bound them.
- `appExit` skips freeing a lock pool and a network lock, because the port's `appInit` does not create them yet.
- `GameEngine.GetLocalizedKeyName` has a stub native entry. The Xbox has none, so binding it would be fatal there.
